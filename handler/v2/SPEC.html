§0
Premise

Why v2 exists

A clean
greenfield
rebuild

V1 — the spy-handler game in handler/ — failed for three reasons. Too many entities for the player to model from text. No time to develop attachment to any character. The handler-from-the-desk framing kept the player emotionally cold.

The deeper authoring problem was that V1 wrote every option by hand — a pre-LLM CYOA discipline that doesn't play to what LLMs are actually good at.

V2 inverts the bargain. Instead of authoring every scene and every option, the author writes a world bible — a grounded description of the place, the people, the truth, and the major beats that constitute uncovering it. The LLM runs scenes inside that world, improvising prose and options. Tools let it advance state when major beats happen. The map keeps the player grounded geographically at all times.

This is closer to playing tabletop with a GM who's read the campaign book than navigating a CYOA tree. The risk is AI-Dungeon drift; the mitigation is heavy world grounding — the LLM cannot invent locations or characters; the truth is fixed; state changes only flow through authored beats.

V1 is not preserved. V2 is greenfield in handler/v2/. No infrastructure is carried over unless it works perfectly for the new system.

“A grounded GM who's already read the campaign book.”
The pitch, one sentence
§0.4
Glossary

Vocabulary  — mental-model hygiene

Up front
so it isn't
surprising
in §3

The engine and the LLM communicate through structured output, not pydantic-ai tool calls. Mental-model hygiene up front saves architecture mistakes later.

state change
A typed field in the LLM's per-turn structured emission. The discriminated union StateChange (see §3.3) has kinds like unlock_beat and move_npc. Not a tool call.
unlock_beat · move_npc
Names of state-change kinds, not tool function names. The model emits them inside a StateChange[] field; the engine applies them after validation.
No tool-call loop
There is no pydantic-ai tool execution layer. No mid-turn tool-result feedback to the model. One LLM emission per turn-phase (see two-stage emission below).
ModelRetry
Pydantic-ai's mechanism for re-prompting when structured output fails application-layer validation (e.g. an unlock_beat whose requires_beats aren't yet satisfied, or whose blocked_by_beats already are). Load-bearing safety against AI-Dungeon drift. Retry budget capped at N=2 per phase.
two-stage emission
Each turn is two LLM calls against the same scene-runner system prompt: (1) StateChangeBundle — state changes only, validated, ModelRetry on failure; (2) ProsePart — prose + next + options, conditioned on the just-applied state. Both share the KV cache because the system prompt is byte-identical.
Warning

If you find yourself wanting “a tool that…”, stop and reconsider. Either it's a new state-change kind (typed field in StateChange), or it requires a real tool-call layer that's currently out of scope.

§0.5
Constraint

Genre fit

This
engine is
built for
a specific
story shape

Documenting the constraint up front prevents wasted weeks on a story the architecture cannot deliver. See §2.4 endings for how this constraint shapes the authored ending model — gated on player-driven decision beats, not on engine-summoned climaxes.

Fits
  • Mystery / investigation. (Pant Goch is this.)
  • Cosmic horror inquiry — Lovecraft, True Detective S1, Disco Elysium.
  • Character study / slice-of-life.
  • Heist — with caveats. Beats encode the plan, but the climactic execution is hard to time.
  • Anything where the player already knows the shape of the ending and the journey is the point.
Does not fit
  • Hero's journey, capital-S Story with a required climax.
  • Action / adventure with a guaranteed setpiece finale.
  • Romance with a mandatory happily-ever-after.
  • Comedy where the punchline must land at a specific moment. (Hot Fuzz: the engine will fight you.)
Why

The LLM judges when story beats fire. The engine has no mechanism to summon a specific beat on schedule — no act breaks, no pacing curve, no railroaded climax. Endings exist as multiple authored options, gated on decision beats the player must explicitly trigger.

If you find yourself authoring beats like the_grand_finale_shootout and wondering how to guarantee they fire at the right moment, the answer is: you can't. Pick a different engine or a different story.

§1
The play loop

Player experience

One
continuous
read

The player arrives in Pant Goch. The screen shows a hand-drawn-style map with ten locations connected by lines; the player's marker is at the Old Vicarage. The vicarage's panel slides in with the opening scene's prose. Below the prose: two to four options.

To leave a location, the player clicks an adjacent location on the map. Their marker walks the line; the previous scene closes with a final line of prose from the scene runner — a closing beat, the door, the rain — and the new location's scene opens.

Inside a scene, the player picks options to drive the conversation. The scene runner improvises responses, generates new options, and decides when a major story beat has been reached — at which point the engine permanently records that beat. Tom named the vehicle. Dylan confessed. Helen handed over the records. The case file in the sidebar updates with each scene's log entry.

There is no day clock, no save points, no XP, no inventory. The game is one continuous read. Scenes last as long as they need to. The investigation advances when the LLM judges, in conversation, that a beat has been earned.

The game ends when the LLM fires one of the authored endings — when accumulated state and player intent line up with what an ending's notes_to_llm describes. The player decides to file the story. The player gives up and goes home. The player is run out of the village.

Locations

Each location is one file in world/locations/. The author writes a rich prose description of the place plus a list of notable details. The map adjacency is declared explicitly.

world/locations/the_slaughtered_lamb.yaml
# world/locations/the_slaughtered_lamb.yaml
id: the_slaughtered_lamb
name: The Slaughtered Lamb
adjacent_to: [the_lane, the_village_green]

description: |
  The village pub. Low ceiling, blackened beams, peat fire smouldering in
  the grate even when it isn't strictly cold enough. Behind the bar: a
  blackboard with prices written in Welsh and English, a row of optics,
  and a faded photograph from a 1987 sheepdog trial.

  Most nights it's six or seven regulars. Mid-afternoon it's usually just
  Old Tom Bevan at the second stool from the door, nursing his bitter.

notes:
  - The fruit machine in the corner is broken and has been since 2003.
  - There's a back room used for funerals and the occasional council meeting.
  - The landlord, Eira Pryce, is Maud's sister-in-law; they don't speak.
  - The pub's name relates to a 19th-c smuggling story, not anything supernatural.

Fields

  • id — unique. Referenced by adjacency lists and cast.yaml default_locations.
  • name — display name in the map UI.
  • adjacent_to — list of location ids. Symmetric, validated at load.
  • description — rich prose. The scene runner pulls this into context whenever a scene plays here.
  • notes — list of strings. Atmospheric and factual details the LLM can weave in. Treat as a fact bank, not a script.

Cast

One file: world/cast.yaml. Each NPC is a richly-described character with themes (what they orbit emotionally), knowledge (what they actually know about the truth), and attitude (how they behave toward the player).

world/cast.yaml — excerpt
- id: tom
  name: Old Tom Bevan
  default_location: the_slaughtered_lamb

  themes:
    - what he saw on the road that night
    - his guilt about not speaking when it would have mattered

  knowledge: |
    On the night of 14 March 2019, Tom was driving home from a friend's
    farm along the B4368, around quarter past eleven. As he came round
    the Black Dog Bend he had to slow for a Land Rover speeding the
    other way — toward Tan-y-coed. He saw it clearly enough in his
    headlights to know whose it was: Eluned Vaughn's. He carried on home.

    The next morning the village knew Megan Pritchard had died on that
    bend the night before. He went to the police and said he'd seen
    "a vehicle." He has never said more.

  attitude: |
    Initially guarded — he has dealt with journalists before and regretted
    it. He is a decent man and will warm to patience, to being seen as
    a person rather than a source. He will close down completely to
    aggressive pressing, to claims of being police or family, or to lies.
    He drinks bitter; he will let the player buy him one.
Implicit state

Every NPC starts at default_location and alive: true. The engine tracks npc_locations and npc_alive dicts; the LLM mutates npc_locations by emitting a move_npc state change. npc_alive exists for forward compatibility but no kill_npc state change is defined in v1.

Truth

One file: world/truth.yaml. This is the most important file. It defines the crime, the beats that constitute uncovering it, and the authored endings.

world/truth.yaml — crime
crime: |
  Megan Pritchard, 19, died on the night of 14 March 2019 on the Black
  Dog Bend of the B4368. The official record says single-vehicle
  accident, blood-alcohol just over the limit. The official record is
  wrong about both.

  Megan had been in a secret relationship with Dylan Vaughn (her

  grand-niece, who lives in Llanidloes) to consolidate two adjacent
  farms. Eluned Vaughn discovered the affair in February 2019. She
  gave Dylan an ultimatum: end it, or lose the farm.

  The night of 14 March, Megan drove out to Tan-y-coed to confront

  She left in tears. Eluned, drunk and furious, took the Land Rover
  and followed her down the B4368 — meaning to confront her face to

  On the Black Dog Bend the Land Rover came too close to Megan's car.

world/truth.yaml — beats & endings
beats:
  - id: tom_named_a_vehicle
    requires_beats: []
    blocked_by_beats: [tom_closes_off]
    description: |
      Tom Bevan tells the player he saw a Land Rover speeding away from
      the Black Dog Bend the night Megan died, and that he recognised
      it as Eluned Vaughn's.
    prerequisites: |
      Tom has been visited at least twice. The player has not lied about
      being police or family, has not threatened him, and has not pushed
      too aggressively in any previous scene.
    notes_to_llm: |
      Tom won't volunteer this. Earn it through patience and the
      accumulated sense of the player being decent. When this moment
      lands, the LLM should narrate Tom's actual words — quiet, finally,
      a relief he didn't know he wanted — and emit unlock_beat with
      "tom_named_a_vehicle". After this, Tom is a different man in
      subsequent scenes: tired, lighter, sometimes weepy.

  - id: tom_closes_off
    blocked_by_beats: [tom_named_a_vehicle]
    # …a negative beat. Author 2-3 per major NPC.

  - id: dylan_admits_he_knows
    requires_beats: [dylan_admits_the_relationship]
    blocked_by_beats: [dylan_refuses_to_speak_again]
    # …chained ordering enforced by the engine

  # Decision beats — fire only when the player has explicitly chosen
  # an ending action. Endings gate on these so the engine never ends
  # the game on inference.
  - id: decided_to_file
    requires_beats: [tom_named_a_vehicle, dylan_admits_the_relationship]
    description: |
      The player has explicitly chosen to write up the story and file
      it with the magazine. This is the point of no return.

endings:
  - id: published_story
    requires_beats: [decided_to_file]
    epilogue: |
      The story runs on Friday in the magazine. The Vaughns are
      questioned within the week. Eluned is charged in early autumn.
      Dylan moves away. You hear, second-hand, that Wendy Pritchard
      sent you a letter — short, almost a card. You did not write back.

Field reference

  • crime — the full truth, written for the LLM to read once at startup. The model is briefed on what's real. It will never have to figure out the mystery; it knows.
  • beats — a list of ~15-25 including negatives and decisions. Each beat is a unit of progress the LLM unlocks by emitting an unlock_beat state-change.
  • requires_beats — engine rejects unlock_beat if any prerequisite isn't in state.unlocked_beats. Triggers ModelRetry.
  • blocked_by_beats — engine rejects unlock_beat if any blocker is in state.unlocked_beats. Triggers ModelRetry. Models failure paths.
  • Negative beats. Author 2-3 per major NPC — tom_closes_off, dylan_refuses_to_speak_again, eluned_throws_you_out. This is what gives "patience" mechanical contrast.
  • Decision beats. One per ending. Encode the irrevocable player choice. requires_beats carries evidence prereqs; notes_to_llm reminds the LLM to wait for explicit player intent.

Validation invariants

The world loader enforces these at startup. Each is a single Pydantic validator.

  1. Location id uniqueness.
  2. Symmetric adjacency. If A's adjacent_to contains B, B's must contain A.
  3. NPC id uniqueness.
  4. Every NPC's default_location references a defined location.
  5. Every beat id is unique across the truth file.
  6. Every ending id is unique. Beat and ending ids share a namespace.
  7. player_starts_at in brief.yaml references a defined location.
  8. Every requires_beats and blocked_by_beats reference resolves to a defined beat id. No self-reference.
  9. The requires_beats graph has no cycles. A cycle would make a beat unfireable; load fails with the cycle path.
  10. Every ending's requires_beats references a defined beat id. Warning if no decision beat present.

That's the entire validation surface. There are no predicates to validate, no exit graphs to check, no effects to parse. The world is mostly prose; the validation is mostly do the few ids resolve, and is the beat graph well-formed.

What the engine does

The engine

Direct
dict
mutations.
No effect
parser.

State

state.py
@dataclass
class State:
    player_location: str                          # id of the location the player is at
    npc_locations: dict[str, str]                 # npc_id -> location_id
    npc_alive: dict[str, bool]                    # npc_id -> alive
    unlocked_beats: set[str]                      # beat ids that have fired
    dialogue_history: list[TurnRecord]            # accumulated turns in the current scene
    game_over: GameOver | None = None             # set when end_game fires

That's the whole state model. No flags dict, no qualities, no effects vocabulary, no scene/storylet ids tracked. The minimum required to gate behaviour: where the player is, where each NPC is, who's alive, what beats have happened.

The scene loop

Each turn is two LLM calls (see §0.4). Validation sits between them; ModelRetry catches semantic violations the grammar sampler can't.

scene.py — RUN TURN
# ---- Phase 1: state changes ----
- build state-change prompt with:
  - location.description + location.notes
  - all NPCs where npc_locations[id] == location_id
  - full unlocked_beats, full unfired-beats list
  - all endings (with their requires_beats)
  - full case-file log (all entries to date)
  - state.dialogue_history (this scene so far)
  - opening_seed if first turn of scene
  - player's last pick (text) if any
- call scene_runner.emit_state_changes() -> StateChangeBundle
  - structured output: list[StateChange] (UnlockBeat | MoveNPC)
  - grammar sampler enforces valid ids
- validate StateChangeBundle:
  - UnlockBeat: requires_beats all in unlocked_beats?
                blocked_by_beats none in unlocked_beats?
  - MoveNPC:    to_location is a defined location?
  - on validation failure: ModelRetry with the specific error, N=2
  - on final failure: drop the offending change, emit SSE warning
- apply validated changes to state in order

# ---- Phase 2: prose + next ----
- build prose prompt (same context plus just-applied state changes)
- call scene_runner.emit_prose() -> ProsePart
  - structured output: prose: str, next: ContinueScene | EndScene | EndGame
- validate ProsePart:
  - if next is EndGame: ending.requires_beats all in unlocked_beats?
  - on validation failure: ModelRetry with error, N=2
- stream prose word-by-word (~80ms/word via paced_word_emitter)
- append turn to state.dialogue_history
- dispatch next

LLM output schemas (two-stage)

schemas — phase 1 & 2
# ---- Phase 1 ----
class StateChangeBundle(BaseModel):
    state_changes: list[StateChange] = []

class UnlockBeat(StateChange):
    type:    Literal["unlock_beat"]
    beat_id: Literal[<the actual authored beat ids>]

class MoveNPC(StateChange):
    type:        Literal["move_npc"]
    npc_id:      Literal[<authored npc ids>]
    to_location: Literal[<authored location ids>]

# ---- Phase 2 ----
class ProsePart(BaseModel):
    prose: str                                # ~80-200 words; streamed
    next:  ContinueScene | EndScene | EndGame  # exactly one

class ContinueScene(BaseModel):
    type:    Literal["continue"]
    options: list[Option]                       # 2-4

class EndGame(BaseModel):
    type:       Literal["end_game"]
    ending_id:  Literal[<authored ending ids>]

All Literal[…] types are built dynamically per call from the loaded world bible. The llama.cpp grammar sampler enforces them at decode time — the model literally cannot emit an invalid beat id, npc id, location id, or ending id. Application-layer validation (requires_beats, blocked_by_beats, ending prereqs) is enforced via ModelRetry between or within phases.

No KillNPC

This story has no in-game deaths. If a future scenario needs one, add it as a new state-change kind; do not pretend it's authored already.

Player-driven leave

When the player clicks an adjacent location during an active scene, the engine hard-ends the scene without offering the LLM a choice to continue. It calls a dedicated closing-prose method on the scene runner — single phase, structured output is just closing_prose: str — passing the destination as context: "the player is leaving for {to_location.name}; write one line of closing prose."

The closing prose streams; SSE scene_exit fires; location_change fires; enter_scene(to_location) runs. No state changes are accepted on the way out. Player agency on movement is absolute.

What the engine does not do

  • No selector. The scene runner is the only LLM agent that makes scene-level decisions.
  • No effect engine. State changes are direct dict mutations on state; there's no effect parser, no predicate evaluator, no set/add/max/min ops.
  • No reactions. No second-pass post-action firing. Everything happens in the turn's state_changes.
  • No tick. No day counter, no automatic time progression.
  • No catalog or eligibility filtering. The LLM looks at the state and the world bible and decides what happens. The engine does not pre-filter possibilities.
§4
Two agents, stable prefix

The LLM layer

Gemma 4
E4B via
llama.cpp

Two agents

Scene runner. Stateless across turns. System prompt baked once at startup (the full world bible). Each turn is a two-phase emission against the same system prompt:

  • emit_state_changes() — structured output StateChangeBundle. Validated; ModelRetry up to N=2 on requires_beats / blocked_by_beats violations.
  • emit_prose() — structured output ProsePart. Conditioned on the just-applied state changes. Validated for ending prereqs. Prose streams word-by-word at ~80ms pacing.

Both phases share the same KV cache because the system prompt is byte-identical. The phase-1 call is short (often empty state_changes: []); phase 2 carries the prose bulk and dominates wall-clock. A third method, emit_closing_prose(to_location) (single phase, schema is just closing_prose: str), serves player-driven leave.

Log writer. Conversation-based, accumulating message_history across scenes. System prompt stable. Each scene-end appends one user message (scene summary) + one assistant message (the case-file entry). OpenAIModelProfile(openai_chat_send_back_thinking_parts=False) is set in lifespan — load-bearing. Without it Gemma 4 drifts in multi-turn.

Scene runner prompt structure

System prompt — stable, baked at startup:

scene_runner.system_prompt
[ROLE]
You are the scene runner for a single-player investigation game set
in a rural Welsh Marches village called Pant Goch. The player is a
freelance journalist investigating the death of Megan Pritchard. You
run scenes turn by turn through structured output.

[THE WORLD]
{full contents of all locations/*.yaml, formatted compactly}

[THE CAST]
{full contents of cast.yaml}

[THE TRUTH]
{full contents of truth.yaml — crime + beats + endings}

[YOUR JOB]
Each turn is two structured emissions against this same system prompt:
  Phase 1 — StateChangeBundle: zero or more state changes
    (UnlockBeat | MoveNPC). The engine validates and applies them.
  Phase 2 — ProsePart: prose (80-200 words) consistent with the
    just-applied changes, plus a `next` directive.

[RULES]
1. Never invent characters not in the cast. Never invent locations
   not in the world.
2. Generate 2-4 options per ContinueScene turn. Options must NOT
   promise a consequence that requires a beat the engine doesn't have.
3. Unlock beats when their notes_to_llm describes the moment.
   The engine will reject (and re-prompt you with the error) any
   unlock_beat whose requires_beats aren't satisfied or whose
   blocked_by_beats already are.
4. End the scene when the conversation has reached a natural stop.
   Aim for roughly 4-8 turns per scene; longer is fine if warranted.
5. End the game only when the player has clearly chosen the action
   that triggers an ending — not just when prerequisites are met.
Note on log size

The full case file and unfired-beats list grow over the playthrough. Estimated steady state at end of game: ~15 log entries × ~100 words + ~25 beats × ~80 words ≈ 3.5k words ≈ 5k tokens of dynamic suffix. The 32k context window absorbs this comfortably; the system prefix (world bible) stays cached.

Model + runtime

  • Model: Gemma 4 E4B (GGUF) via bundled llama-server. Same as v1.
  • Launcher flags: --jinja --flash-attn on --batch-size 512 --ubatch-size 512. KV cache fp16.
  • Sampling: temp=1.0, top_p=0.95, top_k=64. Do not drop temp for "judgment" turns — the model needs creative latitude inside the constraint of the bible.
  • Grammar sampler: llama.cpp grammar sampling enforces the per-call Literal[…] enums. The LLM cannot emit a beat that doesn't exist.
  • KV-cache discipline: system prompt is baked once at startup and never edited. Cache hit rate is the lever for latency.
  • Dev gateway: keep SMALLVILLE_USE_INFERNO=1 env-var pattern. If set, lifespan probes inferno's /health, points pydantic-ai at inferno's /v1.

Single-page web app. Main view is split: map on the left (~40%), scene panel on the right (~60%). The case file is a collapsible sidebar.

  • Map view (always visible). Hand-drawn-style village map with all ten locations and their connecting lines. Player marker at current location. Adjacent locations highlighted as clickable. Non-adjacent locations visible but inert. Clicking an adjacent location walks the marker along the line (~1-2s) and triggers location_change flow.
  • Scene panel. The current scene's prose, streaming word-by-word. Below it: 2-4 option buttons when a turn is waiting on player input. When a scene is closing (EndScene), the prose streams and then the panel dims and the map highlights adjacent locations more brightly.
  • Case file sidebar. Read-only log of completed scenes' entries from the log writer. Scrollable. Collapsible.
  • End-of-game screen. When end_game fires, the ending's epilogue streams in a centred panel. No further input.

§6
Pant Goch & District

Setting bible

Ten
locations.
Nine named
souls.

Pant Goch — "red hollow," Welsh — is a village of ~400 in the Welsh Marches between Knighton and Bishop's Castle. Place-names are bilingual; the language isn't spoken day-to-day. Economy: hill farming, smallholdings, a few Knighton commuters. The pub is the only thing open after six. The post office shuts at four. The primary school has nineteen pupils.

The village sits in a hollow formed by two streams. Bryn Iago Wood rises to the north; Caer Caradoc, an iron-age hillfort, crowns the south ridge. The Black Dog Bend on the B4368 has been associated since at least the 1840s with a folkloric apparition — a large black dog seen before a death. Most locals shrug at it. They also don't drive that bend at speed.

§6.5
Example
scene flow

Player walks to the pub on day 1. Tom is at the bar.

Scene runner is called with: pub description + notes; Tom's themes/knowledge/attitude; empty dialogue_history; full unfired-beats list (tom_named_a_vehicle is in scope but its prereqs aren't met, tom_closes_off blocks it if it ever fires).

Turn 1 — Phase 1

StateChangeBundle(state_changes=[])    # nothing fires yet

Turn 1 — Phase 2 (prose + next)

prose: "The peat fire's going. Old Tom is at the second stool, like
       Mrs Hughes said. He glances up as the door bangs shut behind
       you, then back down at his bitter. 'Bloody door,' he mutters,
       to no one in particular."
next: ContinueScene(options=[
  "Sit at the bar a few stools down",
  "Take the stool next to him",
  "Order a drink first",
])

Player picks "Take the stool next to him." Several turns later, Tom has talked about Megan and expressed his own grief. The player has been patient and not pressed too hard. The scene runner judges Tom is on the edge of saying what he saw.

Turn N — Phase 1

StateChangeBundle(state_changes=[
  UnlockBeat(beat_id="tom_named_a_vehicle")
])

Engine validates: requires_beats=[] ✓, blocked_by_beats=[tom_closes_off] not in unlocked_beats ✓. Applied.

Had the model tried…

…to fire dylan_admits_he_knows here without dylan_admits_the_relationship already in state, validation would have rejected and ModelRetry would re-prompt with: "rejected: dylan_admits_he_knows requires [dylan_admits_the_relationship], not yet unlocked."

Turn N — Phase 2

prose: "He sets the pint down very slowly. Not looking at you. 'Saw
       a Land Rover that night. Going the other way. Past the bend.
       Recognised it.' A long pause. 'Eluned Vaughn's. Knew her
       vehicle since I was a lad and she was a girl.' He looks up.
       There are tears in his eyes that he is not acknowledging.
       'I told them I saw a vehicle. I didn't say whose.'"
next: ContinueScene(options=[
  "'Why didn't you tell them?'",
  "'It's all right, Tom. It's all right.'",
  "Stay quiet.",
])

Subsequent scenes with Tom will play differently because his attitude implicitly shifts — the LLM reads unlocked_beats from state and knows he's already spoken.

§7
Deliberately deferred

Out of scope for v1

Each has
a credible
v1.1+ story.
Numeric qualities

No trust scores, no guilt counters, no coin. State is location + beats + alive.

Generic flags

No set_flag(name, value) kind. All state flows through authored beats. Per-NPC disposition counters were considered and rejected.

NPC schedules

NPCs are static at default_location unless move_npc fires. No "Tom goes home at night" unless authored.

Inventory

Out.

Time / days / clock

Out for v1.

Authored storylets & predicates

The whole v1.0 spec direction. Replaced by the bible + structured-output design.

Salience-weighted picker

Not applicable — there is no "next scene picker"; the LLM constructs scenes from arrival context.

Replay / save slots

Single linear playthrough; close-tab resets.

Authoring tools

Hand-written YAML. LLM-assisted authoring is a v1.1 concern.

Pydantic-ai tool calls

v1 uses structured output across two-stage emissions. No tool-execution layer; the only feedback is ModelRetry.
