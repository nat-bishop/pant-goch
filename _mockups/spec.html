SPEC — Debug Menu Redesign

Status
draft
Owner
Nat
Date
2026-05-07

ScopeReplace the current DEV-only DebugPanel (which renders raw tick_decision SSE events) with a structured, multi-panel debug surface that supports pacing inspection, beat-predicate forensics, agent-call review, player-canon visibility, and tick-level replay.

Terminology

  • Tick — one pass through _tick() (main.py:847). Triggered by a player /send or once at boot for the welcome. Not time-based — there is no background scheduler. Each tick fires at most one beat. Pacing is action-counter / quality driven.
  • Thread — an email thread keyed to one NPC (e.g., aria, cpo). The player can reply on any thread; one tick can fire a beat on a different thread than the one the player replied on (cross-thread first-fires; see main.py:911-914).
  • Beat fire — the engine renders a beat, emitting one or more emails. A beat carries an npc: field, so the sender is determined by the beat, not by the trigger thread.
  • Chat-turn fallback — when _tick returns and no chat-driven beat covered the player's reply thread, _send_stream calls _render_via_chat_agent directly (main.py:1526). This is a chat-agent call outside any TickDecision. One player reply can produce both a plot beat fire (on any thread) and a chat-turn fallback reply (on the reply thread).
  • Snapshot — a frozen GameState after a tick. Global — covers all NPCs and threads. No per-NPC sharding.

1. Goals

  1. Make pacing legible. "Why is commitment at 8?" and "what's stalling secret_path?" should be answerable in seconds, not by tailing logs.
  2. Make beat eligibility explainable. "Why didn't revelation_scene fire?" should resolve to a specific failed predicate atom, not a guess.
  3. Make agent calls inspectable inline. Stop forcing a Logfire round-trip for every classifier/extractor/director question.
  4. Make sessions rewindable. Scrub to any past tick; re-enter from there with a different player message.
  5. Stay read-only. Inspection is the contract — no force-fire, no quality edits, no canon mutations. Authoring tooling lives elsewhere.

Non-goals

  • Mutating live state (force-fire beats, edit qualities, set canon entries).
  • Branching timelines or parallel session forks.
  • Cross-session comparison or A/B-style diffs.
  • Production-user visibility — this is DEV-only and ships behind import.meta.env.DEV.
  • Persistence across server restarts.

2. Audience

A single power user (the dev who is also the author and the playtester). The UI is information-dense by default with progressive disclosure for raw payloads (JSON drawers, expandable tick rows). No role switcher; no curated subset views.

4. Primary view — Pacing

The default view when the debug menu opens.

4.1 Overview: sparkline grid

A compact grid, one row per quality. Each row shows:

ElementBehavior
Quality namePlain text, left-aligned.
SparklineSVG polyline; x = tick index, y = quality value normalized to row range.
Current valueRight-aligned numeric.
Last delta+1 ↑, -2 ↓, ±0 — colored (green/red/neutral).
Click targetWhole row. Drills into §4.2 for that quality.

Hovering anywhere on the sparkline reveals a tooltip with (tick, value, cause) for that x position.

Why sparklines as the default: they answer "shape of the session" in one viewport. Tables and timelines are better for forensic reading but slower for first impressions.

4.2 Drill-down: cause attribution

When a sparkline row is clicked, the quality's full history fills the panel:

curiosity                                              current: 7
─────────────────────────────────────────────────────────────
T1   +1   welcome              literal effect
T2   +1   classify: warm       classifier → curiosity
T4   +1   scene_calibration    literal effect
T5   +1   classify: earnest    classifier → curiosity
T8   +2   revelation_scene     literal, when: trust ≥ 3
─────────────────────────────────────────────────────────────
BLOCKED ON THIS QUALITY
  final_choice    needs cur ≥ 8   (1 short)
  secret_path     needs cur ≥ 10  (3 short)

The blocked-on section is computed by scanning every unfired beat's entry_when for atoms that reference this quality and would currently fail. It answers "what is gated on this number?" without needing to grep the YAML.

4.3 Other lenses (secondary tabs within Pacing)

Available but not default. All three render from the same TickDecision history:

  • Timeline — horizontal scrollable lane of ticks, each cell shows beat name + classifier verdict + delta pills. Best for chronological reading.
  • Deltas table — sortable, filterable spreadsheet. Best for hunting cross-tick patterns.
  • Cause attribution (cross-quality) — the §4.2 view, but listing every quality stacked vertically.

5. Secondary panels

All four ship in v1.

5.1 Tick log

Chronological list of every TickDecision in the session, newest first. Each row collapsed by default; expand to reveal the full JSON:

  • eligibility_report: list of beats considered, with per-beat fired-status and predicate verdict.
  • selection_method: none | sole | continue | director.
  • director_rationale: present only when method = director.
  • effects_applied: literal effects + classify writes + extractor promotions, with before/after values.
  • fired: beat id + render destination (chat-stream | epilogue) + the beat's thread (which may differ from the trigger thread — cross-thread first-fires are common).
  • trigger: thread the player replied on (or "boot" for the boot tick) — surfaces when a CPO beat fires off an Aria reply, etc.

Replaces the current raw tick_decision SSE rendering. Engine-dev essential.

5.2 Player canon ledger

Live snapshot of state.player_canon:

ColumnMeaning
keyCanon key (e.g., name, motivation).
valueCurrent value.
quoteThe verbatim player-text substring that anchored this entry.
salience0.0–1.0 score from extractor.
origin_tickTick when the entry was set or last replaced.
decay_ageturns_since_origin — used to compute the chat agent's top-K view.

A second section shows dropped candidates from the last N=20 player turns — extractor outputs that failed the literal-quote anchor check. Useful for debugging "why did Aria not pick up that I told her my name?" cases.

5.3 Beat inspector — "why didn't X fire?"

Pick any beat (search/dropdown). The panel renders:

  1. Header: beat id, kind (one_shot | scene), npc, thread, ends_session.
  2. Fire status: in fired_beat_ids? if scene, how many fires so far?
  3. entry_when evaluation — atom by atom, against current state:
    • ✅ green for atoms that pass.
    • ❌ red for atoms that fail, with the current value beside the required value.
    • For nested And_/Or_/Not_, indent and render the same way.
  4. exit_when evaluation (scenes only) — same atom-by-atom rendering.
  5. Effects preview — what would mutate if this beat fired right now.

Example:

revelation_scene  (kind: scene, npc: aria)
  fired_beat_ids: false
  entry_when:
    And_:
      ✅ QualityAtLeast(curiosity, 5)        cur=7
      ❌ QualityAtLeast(trust, 5)            cur=4   (1 short)
      ✅ BeatFired(scene_calibration)
      ✅ Not_(BeatFired(revelation_scene))

5.4 Agent trace

A rolling buffer of the last 20 agent calls per agent (chat, classifier, extractor, director, fact-checker, summary). Each entry:

  • Agent name + tick + wall-clock timestamp.
  • Call site: beat_render | epilogue_render | chat_turn_fallback | classifier | extractor | director. Critical for multi-NPC: a single tick can produce a beat-render call (on whichever thread the beat fires) and a chat-turn fallback call (on the player's reply thread); both must show up.
  • npc_id and thread_id when applicable (chat agent + epilogue calls). Lets you filter the trace to "all Aria-thread chat calls" or "all CPO-thread renders."
  • Input prompt (collapsible — these are long).
  • Output (rendered as JSON for structured outputs, plain text for chat).
  • Latency + token counts when available.

The instrumentation wrapper (§7.3) hooks every agent invocation, including _render_via_chat_agent calls outside _tick (the chat-turn fallback at main.py:1526). Without this, multi-NPC sessions where Aria replies via fallback while a CPO beat fires elsewhere on the same tick would show only half the agent activity.

Avoids Logfire round-trips for routine "what did the classifier see" debugging. Logfire stays the source of truth for production traces and historical queries.

6. Replay

6.1 Scrubber UX

A horizontal slider pinned above the chat surface (so it doesn't compete with the panel tabs). Always visible in DEV.

  • Track spans tick 0 (boot) to tick N (latest).
  • Handle is draggable; hovering any tick shows a tooltip (tick N, beat_fired @ thread, classifier_verdict, trigger_thread) — both the fire thread and the trigger thread, so cross-thread fires are obvious.
  • Resume from here button, enabled when handle is not on the latest tick.

6.2 Snapshot model

Server-side ring buffer, keyed by tick index:

class StateSnapshot(BaseModel):
    tick: int
    state: GameState        # full state at end of tick (global — covers all NPCs/threads)
    decision: TickDecision  # what happened during this tick
    agent_calls: list[AgentCall]  # everything captured during this tick (incl. chat-turn fallbacks)

GameState is global — qualities, player_canon, fired_beat_ids, and emails are not sharded by NPC or thread. One snapshot per tick captures the full picture across Aria, CPO, and any future NPCs without per-NPC bookkeeping. Hard truncate (§6.3) restores everything at once; there's no risk of one NPC's state being out of sync with another's after a rewind.

The buffer has no max size for v1 — sessions are short (10s of ticks). Add a cap if memory ever becomes a real problem.

6.3 Resume semantics — hard truncate

When the user clicks Resume from here at tick T:

  1. Server discards all snapshots > T from the ring buffer.
  2. GameState is replaced with snapshots[T].state.
  3. Chat transcript truncates to messages ≤ T.
  4. SSE clients receive a replay_resume event with {tick: T}; the frontend re-syncs from /state.
  5. The next player /send continues forward from T as if T+1 onward never happened.

No branching, no undo of the rewind itself. This is intentional — preserving abandoned tails is a small step toward branching, and we agreed branching is out of scope. If a rewind turns out to be the wrong call, restart the session.

6.4 What's NOT in scope for replay

  • Per-message scrubbing (the unit is the tick, not the SSE chunk).
  • Comparing snapshots side by side.
  • Exporting/importing a session as a JSON bundle.
  • Persistence across server restart.

7. Data model changes

7.1 New types

# npc_service/src/npc_service/models.py

class AgentCall(BaseModel):
    agent: Literal["chat", "classifier", "extractor", "director", "fact_checker", "summary"]
    call_site: Literal["beat_render", "epilogue_render", "chat_turn_fallback",
                       "classifier", "extractor", "director", "fact_checker", "summary"]
    tick: int
    npc_id: str | None = None      # set for chat/epilogue renders
    thread_id: str | None = None   # set for chat/epilogue renders
    started_at: datetime
    duration_ms: int
    prompt: str
    output: str | dict
    tokens_in: int | None = None
    tokens_out: int | None = None

class StateSnapshot(BaseModel):
    tick: int
    state: GameState
    decision: TickDecision
    agent_calls: list[AgentCall]

7.2 ReplayBuffer

A new in-memory structure on the FastAPI app, scoped to the active game session:

class ReplayBuffer:
    snapshots: dict[int, StateSnapshot] = {}

    def record(self, tick: int, state: GameState, decision: TickDecision,
               agent_calls: list[AgentCall]) -> None: ...

    def get(self, tick: int) -> StateSnapshot | None: ...

    def truncate_after(self, tick: int) -> None: ...

    def latest_tick(self) -> int: ...

7.3 Tick recording hook

The snapshot must be recorded at the end of the request (_send_stream), not at the end of _tick — otherwise the chat-turn fallback's agent call (which fires after _tick returns; see main.py:1521-1530) would be missing from that tick's snapshot.

Flow:

  1. At the top of _send_stream (and _boot), reset a per-request ContextVar agent-call buffer.
  2. An instrumentation wrapper around each agent's .run() appends an AgentCall to the buffer with the correct call_site, npc_id, thread_id. The wrapper is the only behavioral change to agents.py — and it's a no-op when not in DEV.
  3. After _tick runs and after any chat-turn fallback render, snapshot the final GameState.
  4. replay_buffer.record(tick, state, decision, agent_calls) — agent_calls now includes both beat-render and fallback-render calls when both happened on this tick.

8. API changes

8.1 New endpoints

MethodPathPurpose
GET/debug/snapshotsList tick + small summary for every snapshot.
GET/debug/snapshots/{tick}Full StateSnapshot for one tick.
POST/debug/resume/{tick}Hard-truncate to tick. Returns the new live GameState.

All under /debug/*, registered only when DEBUG_API_ENABLED=true in env. Frontend gates calls behind import.meta.env.DEV.

8.2 New SSE event

type ReplayResumeEvent = {
  type: "replay_resume";
  tick: number;
};

Broadcast after a successful POST /debug/resume/{tick}. Frontend reacts by clearing local message state and re-fetching /state.

10. Acceptance criteria

  • Sparkline grid renders one row per quality and updates live as ticks fire.
  • Clicking a sparkline row shows §4.2 cause attribution + blocked-on list.
  • Tick log shows every TickDecision with expandable JSON.
  • Canon ledger lists current entries plus the last 20 dropped candidates.
  • Beat inspector resolves any beat to a per-atom predicate verdict.
  • Agent trace holds last 20 calls per agent, prompt + output visible.
  • Scrubber slider drags to any past tick; tooltip shows beat + verdict.
  • Resume from here truncates the server buffer and broadcasts replay_resume.
  • After resume, the next /send continues forward from the truncated state.
  • None of the new code ships in production builds (!import.meta.env.DEV short-circuits the panel; DEBUG_API_ENABLED=false returns 404 from /debug/*).

11. Open questions

  1. Tooltip cost. Computing per-tick cause for every sparkline pixel may be expensive. If perf bites, downsample to "one cause label per tick band" rather than per pixel.
  2. Agent-trace memory. 20 calls × 6 agents × full prompts could be hundreds of KB per session. Acceptable for DEV; revisit if we ever ship to a hosted demo.
  3. Beat inspector for Or_ predicates. Atom-by-atom rendering for Or_ is ambiguous — do we show every branch's status, or just the first satisfying branch? Default to every branch, since the debug intent is comprehensive.
  4. Scrubber + multi-turn scenes. Scrubbing into the middle of a multi-turn scene then resuming should re-enter the scene cleanly because the scene stays out of fired_beat_ids until exit. Confirm with a test before shipping.

12. Out-of-scope follow-ups

These came up during design but are explicitly deferred:

  • Authoring mutations. Force-fire, quality editor, canon editor — belong in a separate authoring tool.
  • Session export/import. Useful for bug reports; revisit once replay is stable.
  • Branching timelines. Big scope jump; not justified by current pain.
  • Production-user debug surface. Different audience, different vocabulary.
